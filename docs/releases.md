# Automated releases

Pushing a `v<version>` tag runs `.github/workflows/release.yml`. Both Linux and Windows builds must pass the test suite and frozen command smoke checks before a GitHub release is published:

- Linux x86_64: standalone `.tar.gz` (built on Ubuntu 22.04; requires glibc 2.35 or newer).
- Windows x86_64: standalone portable `.zip`, including `issueboard.exe` and `_internal` dependencies.
- Python wheel and source distribution (built on Linux).
- SHA-256 sidecars for all downloads.

The Linux and Windows packages include Python and the app dependencies; users do not need Python, uv, or a checkout. GitLab integration still requires `glab` and its own login. Linux credential storage needs a working Secret Service or KWallet session. Windows uses Windows Credential Manager. [Windows testing and WinGet submission](windows.md).

macOS users should install with [Homebrew](homebrew.md). No macOS binary or installer is generated by this workflow.

For an archive, extract the entire folder and run `./issueboard-<version>-<platform>-<arch>/issueboard --help`. Keep `_internal` beside the executable. Add the extracted folder to your PATH if desired. Verify downloads with `sha256sum -c <asset>.sha256` on Linux. The repository and release downloads are public; no authentication is required. See the [Linux installation commands](../README.md#linux-download-and-run).

## Publish

1. Set a new `MAJOR.MINOR.PATCH` version in `pyproject.toml`, then run `uv lock` and `uv sync --locked --group release`.
2. Run `uv run pytest -q`, commit the changes, and push the commit with the workflow included.
3. Tag that commit and push the tag:

   ```sh
   git tag -a v0.3.3 -m 'Issue Board 0.3.3'
   git push origin v0.3.3
   ```

Use the actual new version. The workflow rejects a tag that differs from `pyproject.toml`. GitHub Actions must be enabled and repository policy must permit the publishing job's `contents: write` permission. Only the built-in `GITHUB_TOKEN` is needed; no personal token or extra release secrets are required. Existing releases are never overwritten. If an upload fails after creating a draft, inspect and delete the incomplete draft before rerunning the workflow.

To test the pipeline before a release, run it manually from the Actions tab: it tests and uploads build artifacts without publishing a release when run on a branch. Download artifacts within seven days.

WinGet manifests are generated from the Windows ZIP and uploaded as a separate **winget-manifests** CI artifact. Submission to Microsoft is a separate step described in [Windows and WinGet](windows.md). This is preparation for the next Windows release, not a claim that the current version is in the WinGet catalog.

Homebrew tap updates remain a separate step described in [Homebrew distribution](homebrew.md); this workflow does not push to the tap or publish to PyPI.

## Build locally

On Linux, with Python 3.12+, uv and `binutils` (for example `sudo apt install binutils`):

```sh
uv sync --locked --group release
uv run python scripts/build_release.py
```

Outputs are in `dist/release/`. The executable and its tracker subcommands’ `--help` is checked after freezing. Builds are native to the architecture used. On Windows x64, run the same uv commands in PowerShell (no binutils needed); the output is a ZIP and checks also run after extraction. macOS continues to use Homebrew.
